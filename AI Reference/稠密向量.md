# 稠密向量（Dense Vector）

> 稠密向量是绝大多数分量都非零的向量。在 LLM 应用中，它常用于表示文本的语义，让程序能够用数值计算比较文本的相似程度。

## 1. 从直觉理解

向量可以先理解成一个有顺序的数字列表：

```text
[0.12, -0.34, 0.87, 0.06]
```

这个向量有 4 个维度，且每个分量都非零，因此是一个稠密向量。实际文本表示的维度由模型和配置决定，上面只是演示。

假设要比较下面三句话：

- A：「如何重置密码？」
- B：「忘记密码后怎样重新设置？」
- C：「今天北京的天气怎么样？」

合适的文本 embedding 模型通常会让 A、B 的向量更接近，而让它们与 C 的向量相对远一些。这样，即使两句话的用词不同，也有机会通过语义相似度找到彼此。

**这里有两个不同的概念：稠密描述数值的分布；语义来自模型的训练。** 随机生成一组非零数字也是稠密向量，但不因此具有有用的语义。

## 2. 稠密向量与 Embedding 的关系

Embedding（嵌入）是把文本、图片等对象映射为向量表示的过程，也常用来指得到的表示。在语义检索中，文本 embedding 通常采用稠密向量。

```text
文本 → embedding 模型 → 稠密向量 → 相似度计算 → 检索结果
```

这两个词并不完全等价：

- **Embedding** 强调「对象如何被表示」。
- **稠密向量** 强调「向量的大多数分量非零」。
- Embedding 也可以采用稀疏表示；稠密向量也可以表示与文本无关的数据。

在学习得到的文本向量中，一个维度通常不能直接命名为「天气」「情绪」或「密码」。语义由多个维度共同编码，维度中的负值也不表示负面情绪。

## 3. 与稀疏向量有什么区别？

稀疏向量（Sparse Vector）的绝大多数分量为零。例如，在一个很大的词表中，一篇短文只涉及少量词，便可以只在对应位置记录非零权重。

| 对比项 | 稠密向量 | 稀疏向量 |
| --- | --- | --- |
| 数值分布 | 绝大多数分量非零 | 绝大多数分量为零 |
| 简化示例 | `[0.2, -0.5, 0.8, 0.1]` | `[0, 0, 0.8, 0, 0, 0.3, 0, 0]` |
| 文本中的典型表示 | 模型学习的语义 embedding | 词袋、TF-IDF、学习型稀疏表示 |
| 维度含义 | 通常不能逐维直接解释 | 词表型表示的维度通常对应词或 token |
| 常见检索优势 | 匹配同义表达、语义相近的内容 | 匹配专有名词、编号等明确词项 |
| 常见存储方式 | 存储所有分量 | 仅存储非零分量的位置和数值 |

「稠密」不等于「维度高」，「稀疏」也不等于「维度低」。稀疏向量可以拥有非常多的维度，只是大部分位置为零。

检索效果取决于模型、数据和任务。工程上常采用**混合检索**，结合关键词检索与稠密向量检索，再融合结果或进行重排。

## 4. 如何比较两个向量？

常见方法包括余弦相似度、点积和欧氏距离，其中余弦相似度比较的是两个非零向量的方向：

$$
\operatorname{cosine\_similarity}(\mathbf{q},\mathbf{d})
= \frac{\mathbf{q}\cdot\mathbf{d}}{\|\mathbf{q}\|_2\|\mathbf{d}\|_2}
$$

- 数学取值范围为 $[-1,1]$，数值越大表示方向越接近。
- 如果两个向量都已进行单位长度归一化，点积就等于余弦相似度。
- 相似度分数不是「答案正确的概率」；`0.8` 不代表 80% 正确，也不存在适用于所有模型的统一阈值。

例如，查询向量 `[1, 1]` 与候选向量 `[2, 2]` 的余弦相似度是 `1`：它们长度不同，但方向相同。这里使用手工数字演示数学关系，不代表真实模型输出。

**比较向量时必须使用兼容的表示空间。** 实践中通常使用同一个 embedding 模型，或明确配套的查询与文档编码器；仅仅维度相同，不意味着两个模型生成的向量可以直接比较。距离度量也应遵循模型的使用约定。

## 5. 在 LLM 与 Agent 中有什么用？

### RAG：为回答检索参考资料

```text
准备资料：文档 → 分块 → embedding → 存入向量索引
用户提问：问题 → embedding → 检索相近片段 → 将片段原文交给 LLM → 生成回答
```

稠密向量在这里主要负责「找资料」。典型文本 RAG 交给生成模型的是检索到的文本片段，而不是直接让模型阅读向量中的数字。检索到的内容是否正确、是否足以回答问题，仍需要进一步判断。

### Agent 记忆：召回相关历史

将历史对话、任务记录或经验生成 embedding，便于 Agent 在新任务中检索相关内容。这是一种外部记忆方案，不等于修改了 LLM 的模型参数。

### 语义路由：选择候选处理流程

将用户请求与预先定义的意图示例比较，例如「查天气」「检索知识库」「查询订单」，再根据相似度选择候选路线。

向量相似度可以辅助路由，但不等于完成工具调用、权限判断或参数校验。相关笔记：[[LLM Rewrite 资料]]。

### LLM 内部表示：注意区分用途

LLM 内部的 token embedding 和隐藏状态也常表现为稠密向量，但它们不自动等于适合句子检索的 embedding。直接取某层隐藏状态做平均，不保证得到高质量的语义检索表示；效果与训练目标、取层及聚合方式有关。

## 6. 实践中容易误解的地方

- **不是压缩后的原文文件。** 文本 embedding 通常不能无损还原原文，因此检索系统需要保留原文或可回溯的引用。
- **维度越高不一定越好。** 效果还取决于训练数据、任务匹配程度和文档分块等因素；更高维度通常增加存储与计算开销。
- **语义相近不等于事实一致。** 「支持退款」与「不支持退款」讨论同一主题，向量可能接近，但含义存在关键差异。
- **更换模型通常需要重新编码资料。** 不能只更新查询侧模型，就默认它仍能与旧文档向量兼容。

一句话记忆：**稠密向量是数值表示形式；embedding 模型赋予表示可用于任务的结构；检索系统利用这种结构寻找相关内容。**
